`@antasphere/cli` is the `antasphere` command-line client — the account CLI
for the Antasphere hub. One `antasphere login` mints a
workspace-bound API key over the browserless email-OTP surface and
stores it in a local profile; every later command rides that profile. The
surface mirrors what an API key can reach through the fail-closed scope
allowlist: identity, organizations, files, and — with the opt-in
`data:export` scope — the workspace export.

## Install

`npm i -g @antasphere/cli` exposes the `antasphere` binary. The published
package is a single self-contained bundle (`dist/bin.js`, built with esbuild):
the workspace-internal `@antasphere/contract`, `@antasphere/sdk`,
`@antasphere/cli-core`, and commander are inlined at build time, so the
published manifest carries **zero runtime dependencies** — nothing internal or
git-pinned leaks into a public install.

From a checkout:

```bash
pnpm --filter @antasphere/cli... build
node packages/cli/dist/bin.js --help
```

## Sign in

```bash
antasphere login                 # prompts for email + the 6-digit mailed code
antasphere login --email you@example.com --key-name laptop --expires-days 90
antasphere whoami                # user + organizations + the active org
antasphere logout                # revokes the key server-side, clears the profile
```

`login` drives the public `/cli/auth/request` + `/cli/auth/complete`
surface: the code proves the mailbox, the minted key carries
`account:read` + `account:write` + `sso:exchange` (never `data:export`;
`sso:exchange` is the cross-tool token exchange at `POST /sso/tool-token` —
federated tool CLIs trade the hub key for a short-lived
tool-local credential, one hub login for every tool), appears exactly once,
and goes straight into the config file. On the hub's open instance
a first login for a fresh email IS the onboarding: account + personal org +
key in one flow. 2FA-enrolled accounts are refused
(`two_factor_required` — mint a key in the dashboard instead).

`logout` calls `DELETE /cli/auth/key` — a key may revoke exactly ITSELF —
then removes the profile (an already-dead key still clears the profile).

## Configuration

Profiles live at `~/.config/antasphere/config.json`
(`$XDG_CONFIG_HOME/antasphere/config.json`; directory 0700, file 0600 — it
stores the API key). The store is the `hub` namespace of the shared
Antasphere CLI config home owned by `@antasphere/cli-core` (extracted from
this CLI); other tool CLIs keep their profiles under
`~/.config/antasphere/tools/<tool>.json` in the same home. `--profile <name>`
selects one; `login` writes the selected profile and marks it active.
Resolution per setting:

| Setting  | Precedence                                                                  |
| -------- | --------------------------------------------------------------------------- |
| Base URL | `--api-url` → `ANTASPHERE_URL` → profile → `https://account.antasphere.com` |
| API key  | `--api-key` → `ANTASPHERE_API_KEY` → profile                                |

Dev instances: `antasphere --api-url http://localhost:3200 login` stores the
URL in the profile, so later commands need no flag.

## Commands

```bash
antasphere login                          # email OTP → stored API key (see above)
antasphere logout                         # revoke the stored key + clear the profile
antasphere whoami                         # user, orgs, active org, scopes
antasphere org list                       # your organizations (active org marked *; alias: orgs)
antasphere org use <id>                   # pick the org tool CLIs exchange this login for
antasphere org use --unset                # back to the org the key was bound to at login
antasphere instance                       # discovery: name, version, auth methods
antasphere export [-o <path>]             # full org export as a zip (needs data:export)
antasphere files list                     # list org files (newest first)
antasphere files upload ./report.pdf      # upload (name defaults to the basename)
antasphere files download <id> --out ./f  # download by id
antasphere files rm <id>                  # delete by id
```

The key is bound to ONE organization at mint — `whoami` and
`org list` mark the active org with `*`. For HUB commands in another org,
log in again into a second profile: `antasphere --profile acme login`
(a per-org key each, the gcloud/gh model).

`org use <id>` does something different: it does not change what this hub
key can reach — it stores the ACTIVE org that federated TOOL CLIs (e.g.
`slideless`) read as their org context. Since the Phase-6 cleanup the
exchange itself (`POST /sso/tool-token`) is org-free — the minted tool
credential identifies the USER, and the org any tool operation
targets is a per-request selection tool-side — so this choice steers tool
CLIs' selection, never what the exchange mints. The choice lives on the
hub profile; `--unset` clears it, and a tool-side `--org <id>` flag
overrides it per invocation. `org use` validates the id against
`GET /orgs` before storing it.

`export` needs a key granted the opt-in `data:export` scope (never implied
by `account:read`) and an admin+ creator; the zip streams to disk (default
`export-<yyyy-mm-dd>.zip`). Account deletion is deliberately NOT in the
CLI — it is a session-only act (see [security.md](/antasphere/security/security)).

`files list` is cursor-paginated (server default 50, max 100 per page):

| Flag                | Effect                                          |
| ------------------- | ----------------------------------------------- |
| `--limit <n>`       | Page size (1-100)                               |
| `--cursor <cursor>` | Resume from a previous page's `nextCursor`      |
| `--all`             | Follow `nextCursor` until every page is fetched |

Human output prints a `More available: rerun with --cursor <id> or --all`
hint when a page remains; `--json` prints the wire shape
`{ files, nextCursor }` (with `--all`, all rows and `nextCursor: null`).

Add `--json` to any command for machine-readable output. A non-2xx response
prints to stderr and exits non-zero; a scope denial (a read-only key trying
to write) is a clean `403` message.

## Example (agent-style)

```bash
antasphere login --email agent@example.com     # once; the profile stores the key
antasphere whoami --json | jq .workspace.name
antasphere files upload ./out.csv --content-type text/csv --json | jq -r .file.id
```

Ephemeral environments can skip the config file entirely:

```bash
export ANTASPHERE_URL=https://account.antasphere.com
export ANTASPHERE_API_KEY=ant_xxx_yyy
antasphere whoami --json
```
